# Private lifecycle control and evidence (u24, v24)

After `READY`, the explicit disposable runtime exposes one private, bounded
lifecycle endpoint over its **actual** surviving owners. It is the operator
harness's only way to invoke the supported [C9 same-owner restart](restart.md),
to arm the one-shot [response-exposure lost-reply fixture](#lost-reply-fixture-v24)
and to collect actual source/ledger evidence from a live runtime. It adds no
normal publication, guest RESUME, replacement exporter/FUSE/native owner or
recovery after owner loss. READY and every evidence record carry `publication: null`; the OBSERVED and
restart-outcome wrappers carry no publication key at all.

## Endpoint and authority

* The socket is `OwnerDirectory/control.sock`, created exclusively inside the
  private `0700` owner root (an existing name, including a symlink, is preserved
  and refused), mode `0600`. The endpoint holds an `O_NOFOLLOW` handle of the
  owner root (checked to be this account's private directory) and does every
  post-bind step relative to it without following a symlink: it confirms the
  bound name is its own socket, records that inode, sets `0600` with
  `fchmodat(AT_SYMLINK_NOFOLLOW)` (Linux: `fchmodat2`, or on kernels before 6.6
  an `O_PATH|O_NOFOLLOW` handle pinned to the recorded inode) and re-checks the
  same inode has exactly `0600`. A name swapped in between is refused, never
  chmodded. Between bind and that change the socket has the umask's mode, but
  only this account can traverse the owner root. There is no guest, network,
  abstract or reconnect listener. Closing removes only that unchanged socket
  inode (a replaced name is preserved and reported). Configuration validation
  refuses an owner directory whose socket path would not fit `sockaddr_un`
  (103 bytes), before any owner is created.
* Each connection is authenticated by the kernel peer credentials before any
  request byte is read (Linux `SO_PEERCRED`, FreeBSD `LOCAL_PEERCRED` with the
  checked `xucred` ABI, through the narrow `admin.PeerCredentials` helper). Only
  the daemon's effective UID is accepted. No admin/recovery/audit API is reused.
  An unauthorized peer gets a REFUSED frame and the connection closes at once,
  so the client's request write may fail with EPIPE while that refusal is
  already queued. The client then still reads the reply and reports it, but only
  if it is a refusal (task 564).
* `READY` announces `control: {socket, runtime, cut, epoch}`. The runtime UUID
  and cut UUID are generated by the server; the epoch starts at 1. Commands name
  this binding; they never carry Facts, native handles, sources, owners, paths
  or pass/fail values.

## HSC1 framing

Every frame has a 16-byte header: `"HSC1"`, version 1, opcode, two zero bytes,
big-endian uint32 sequence and big-endian uint32 payload length. One connection
carries exactly one request and one reply.

| Opcode | Request payload (fixed length) | Reply |
|---|---|---|
| 1 OBSERVE | runtime UUID (16 bytes) | `{"status":"OBSERVED","sequence":N,"evidence":{...}}` |
| 2 RESTART | runtime UUID, current cut UUID, uint64 epoch (40 bytes) | restart outcome with post-attempt evidence |
| 3 ARM_LOST_REPLY | runtime UUID, current cut UUID, uint64 epoch, session UUID, operation code: 1 any CALL, 2 MKDIR CALL only (57 bytes) | `{"status":"ARMED","sequence":N,"lost_reply":{...}}` |

Replies use opcode `request|0x80`; frame-level refusals use `0xff`. Unknown
opcodes, wrong lengths (checked before any payload read or allocation), bad
magic/version/reserved bytes and sequence zero refuse. An oversized OBSERVE
reply refuses. `{"status":"REFUSED","reason":...}` means the command took no
effect, so a command that may already have taken effect never answers REFUSED:
a RESTART outcome that does not fit is reported as `EFFECT_UNREPORTABLE` (see
[RESTART](#restart)), and the frame backstop for an oversized RESTART or ARM
reply is `{"status":"EFFECT_UNREPORTABLE","reason":...}` (ARMED is a fixed-size
record, so that backstop is not expected to be reached).

The sequence must be strictly greater than the last accepted sequence. A wrong
runtime UUID or non-monotone sequence refuses without consuming it; any other
accepted command consumes its sequence even if refused later (for example a
stale cut). After a lost reply, the client sends a larger sequence and uses
OBSERVE, which needs only the runtime UUID, to learn the current cut/epoch.

`hfs-controlled-runtime --control SOCKET --operation
observe|restart|arm-lost-reply --runtime UUID --sequence N [--cut UUID --epoch
N [--session UUID --lost-operation CALL [--lost-intent MKDIR]]]` is the
matching one-shot client (`--lost-intent MKDIR` sends operation code 2); it
prints the raw reply and exits non-zero on refusal (FENCED and
EFFECT_UNREPORTABLE are consumed attempts, not refusals, and exit zero). Flags
belonging to another operation refuse.

## OBSERVE

OBSERVE refreshes **every** actual `Admission` through its pinned guest observer
(a failed or changed observation fences that Admission exactly as any refresh
does; nothing is retried) and captures, from the current actual owners:

* supervisor issuance stage, process, controller, endpoint, live check and the
  bounded s24 exporter diagnostics snapshot;
* per Admission: refresh error, fence, boot, provider nonce, kernel build,
  physical inventory hash and every domain's phase/revision/fence;
* service state, journal incarnation/owner/generation/configuration and a fresh
  complete view source (`Through`, `Applied`, visibility, state hash/bytes)
  taken on the service worker within the signed `SourceBytes`;
* each provider's protected ledger digest (the digest C9 compares), inode and
  size under its execution mutex, and (evidence `/2`, b84) a bounded claim
  summary from the same read transaction: principal count, the sums of every
  principal's allocated high-water and retirement floor, present entries, the
  number of open entries (neither TERMINAL nor a declined gap), up to 16 open
  entries oldest first and the 8 newest entries, each as number, guest
  opcode, ledger status and preparation stage only (no binding, credential,
  name or process identity). There is no age: the ledger stores no time. The
  zq3 bootstrap's `usable` gate uses it to require that the probe children's
  GETATTR and PROCESS_EXIT claims reached TERMINAL;
* the view controller's protected ledger digest, size, whether the live state
  equals those protected bytes, and inert counts;
* the live C8 ledger index (controller, endpoint, high-water, cells, classes,
  workspace, terminal/HELLO witnesses, guest high-water) and its full digest,
  read under the transport mutex so the cut equals the last protected transition;
* after a successful ARM, the `lost_reply` section: the server-issued fixture
  UUID, the arming cut/epoch/session, funded bytes, the service source identity
  captured at arming (`baseline`) and the armed transport's actual exposure
  record, read from that transport even after a restart switched owners.

Each section reports its own error text (truncated to 512 bytes) instead of
inventing a value. `complete` only means every section was captured without
error and the lifecycle is not FENCED; it is not an acceptance flag. Closed,
suspended, absent or partial owners are reported as such. An external
invocation/reply oracle must correlate these records.

OBSERVE replies (only) also carry `endpoint`: the number of accept failures
since READY and the last one's text. They do not affect `complete`; see
[Bounds and funding](#bounds-and-funding) for how they are handled.

## RESTART

RESTART requires the exact current runtime, cut and epoch and the SERVING stage.
It then consumes the single attempt (a fresh cut and incremented epoch are
issued whatever happens) and calls the real `Supervisor.SuspendEndpoint`,
`Restart.Reopen` and `Restart.Activate` on the retained Producer/Transport:

* success switches the lifecycle's current owners to the reopened
  service/Facts/providers/controller/Producer/Transport (stage RESTARTED); the
  native shell dispatch was switched and the same C exporter resumed by
  Activate;
* failure (step `suspend`, `reopen` or `activate`) leaves the supervisor fenced,
  blocks admission on every reachable service and retains all original and
  nonnil partial owners (listed in `partial_owners`) until runtime exit. There
  is no rollback, exporter resume or owner deletion. Fencing closes the native
  management channel, so the runtime then ends as on any owner loss, retaining
  files, mount and VM resources.

The outcome plus its post-attempt evidence is protected in the exclusive owner
file `control-restart.json` (at most 124 KiB) before the reply is written; an
existing file is preserved and the reply then carries `protect_error`, as do
later OBSERVE `restart` sections. If the outcome with its evidence would not fit
that bound, the attempt is still never reported as refused: the protected record
and the reply use status `EFFECT_UNREPORTABLE`, `outcome` keeps the actual
RESTARTED/FENCED result, step, error, barrier, physical hash, epoch, cut and
partial owners are kept (all bounded), and only `evidence` is replaced by
`evidence_error` naming its encoded size; OBSERVE then reports the current
owners, and its `restart` section keeps the actual status. The remaining 4 KiB
of the 128 KiB reply bound are reserved for `protect_error`, whose 512-byte
text JSON escaping can grow sixfold. A later RESTART always refuses. Without a
native shell-switch primitive the operation refuses before any effect (it
consumes its sequence, but no attempt, cut or epoch). An armed, unfired lost-reply fixture is expired before suspension;
it never crosses C9.

A C9 cut after a filesystem mutation additionally needs the guest steps any cut
needs: no active lookups (FORGET the returned capabilities) and no historical
view source, so the guest refreshes its view (VIEW_ACQUIRE, a complete recall
release and VIEW_RETIRE through the runtime's own ticket families) before
RESTART. Otherwise transport suspension or controller reopen refuses and the
runtime stays fenced, as for any unsupported cut.

## Lost-reply fixture (v24)

ARM_LOST_REPLY arms one disposable, exact one-shot fixture inside the actual
`guestbridge.Transport.Read`, which is the protected response exposure that the
native exporter's result-node `pread` reaches through the FUSE
`PrivateControl.Read` callback. It requires the SERVING stage, the exact
current runtime/cut/epoch, an enrolled session and operation code 1 (any
`CALL`) or 2 (only a `CALL` whose guest intent opcode is `MKDIR`, d44);
any other code, a stale or consumed binding, an unknown session, any ARM after
one succeeded (even once it fired or expired) or an exhausted budget
refuses. Before the transport is armed the endpoint reserves the fixture's own
admission lease and captures the service source baseline; a refusal releases
the lease and arms nothing, so it consumes no one-shot. ARM itself does not
rotate the cut. The fixture is armed only on a transport owned by a disposable
validation service.

The predicate takes no response, result, Facts, bytes or caller values. It
matches only the first nonempty result-node exposure of a `CALL` cell in the
armed session that was accepted after arming (its native cell is above the
recorded `armed_high`), is fully responded (so its effect, claim and response
are already protected), has no covered byte yet and, with code 2, carries the
intent opcode `MKDIR` in its own accepted command; other CALLs are exposed
normally and leave the fixture armed. That Read computes the
chunk, then returns EIO with no bytes and leaves read coverage unchanged,
because nothing reached the native reader. The record (`exposure`) names the
armed `intent` filter (absent for code 1), the actual native cell, claim,
`dropped_opcode`, command/response/dropped-chunk digests, wire and unread
bytes, job phase and outcome `UNCERTAIN`.

Code 2 exists because the Linux guest's `mkdir(2)` always sends GETATTR and
LOOKUP CALLs before MKDIR (and background FORGET/PROCESS_EXIT CALLs may race
in), so code 1 practically never drops the mutating reply, and no guest
warm-up can avoid those CALLs; see the
[guestbridge analysis](../guestbridge/README.md#targeting-the-mkdir-reply-d44).
A runtime built before d44 refuses code 2 as an unsupported operation. All later reads, including the
retry of the same chunk, deliver the identical protected bytes; nothing is
re-executed, reclassified or written to the C8 ledger. An unfired fixture is
expired before a C9 suspension. The record lives only in daemon memory; an
external oracle must OBSERVE it, and a daemon crash loses an unobserved record
without inventing one.

Recovery is the guest's: resolve the uncertain result by claim (QUERY returns
the original result), re-read the retained CALL cell, then, if wanted, the real
C9 restart. A C9 attempt while the dropped response is still unread by the
exporter refuses at the paired exporter/C8 cut (the C row has no response) and
stays fenced; C9 does not fabricate the missing exposure.

## Bounds and funding

A single worker accepts and serves connections strictly serially, so OBSERVE,
ARM and RESTART never overlap. Each connection has a 5 s I/O deadline for its
request and reply; OBSERVE and ARM have 30 s and RESTART 90 s (the C9 grant
itself expires after 60 s). Requests are at most 73 bytes; replies at most
128 KiB.

A transient accept failure (`EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`, an aborted
or interrupted connection) never ends the worker: it is counted in OBSERVE's
`endpoint` section and retried after a backoff of 5 ms doubling up to 1 s
(reset by the next accepted connection; closing the endpoint interrupts it).
Any other accept failure is permanent: the worker ends and the runtime ends as
on owner loss (admission blocked, every owner, file, mount and VM resource
retained), returning `lifecycle endpoint accept failed permanently: ...`, rather
than serving on without its only control endpoint.

`fundRuntime` reserves a separate admission lease for this endpoint before any
owner exists: one worker, one connection and
`1 MiB + C8 peak (128 KiB + 8 MiB + 8 MiB) + 2 × LedgerBytes + 3 × SourceBytes`.
The host budget check includes it and `runtime-budget.json` records it under
`Control`, with the 128 KiB `control-restart.json` disk bound. The lease is
returned only after the endpoint's worker joined. The lost-reply fixture has a
separate 64 KiB Memory lease (one operation, no worker or connection) for its
record, claim copy, digests and source baseline; the host budget check
pre-accounts it (a host budget one byte short refuses) and
`Control.LostReplyBytes` records it. The runtime Memory pool's limits count one
operation and those bytes for it, but nothing is held in advance: ARM reserves
the lease only when it arms, and runtime close returns it. After assembly no
other runtime owner reserves from that pool (a C9 restore transfers the
suspended transport's leases), so the slot is normally free; if anything took
it first, ARM refuses as unfunded and arms nothing. Closing the endpoint stops
accepting and joins the bounded in-flight command (its reply and protected
outcome are not truncated by an owner-loss shutdown); parent cancellation still
propagates into that command.

## Evidence boundary

`lifecycle_test.go` drives the shared command driver through actual proposal,
signed handoff, real supervised C strong startup/backend/ledger and HELLO to
READY, then uses the real endpoint and client: actual OBSERVE evidence is
compared with the live owners; a real C9 restart pauses/binds/resumes the actual
C exporter over HSR1, reopens all owners from their files and serves a further
original scope through the restored transport. Negative tests cover foreign
and unavailable peer credentials, malformed/oversized/short frames, a stalled
partial frame at the deadline, wrong runtime, repeated/lower sequences, stale
cut/epoch, repeated restart, inconsistent guest physical state (truthful fenced
evidence and a FENCED suspend) and a refused native switch (FENCED activate with
retained partial owners). The kernel peer credentials (when a test says so),
native mount/INIT/fd syscalls, FUSE shell dispatch switch and observed guest
physical state are explicitly substituted OS boundaries.

`lifecycle_hardening_test.go` adds, on further real runtimes: RESTART without
a native shell switch (refused before any effect, sequence consumed, binding
and stage unchanged, no outcome file); simulated `EMFILE` at the accept
boundary at startup and after a served connection (retried, counted in
OBSERVE) and then a simulated `EINVAL` (the runtime ends with that diagnostic,
the VM stand-in alive, socket and control funding returned); and a guest
physical state that changes between the attempt's suspend and reopen refreshes
(served through a FIFO at the observation boundary), giving a FENCED `reopen`
step with retained partial owners, while a pre-existing `control-restart.json`
makes the real protection fail (`protect_error`, file preserved). Unit tests
use real types and a real exclusive supervisor owner directory: the
EFFECT_UNREPORTABLE bound with worst-case `protect_error`, every protection
refusal (unencodable, oversized, existing file, closed directory), socket
creation in a private root with exact `0600`, refusal of existing files and
symlinks and of non-private or symlinked owner roots, a socket name swapped for
a symlink after bind (target untouched, name preserved), the Linux pre-6.6
pinned-handle chmod, accept error classification and backoff bounds.
`TestRuntimeFundingHostBoundary` funds the exact host sum (and refuses one byte
less), assembles the runtime and then reserves the lost-reply lease, leaving
the Memory pool exactly full. An oversized post-attempt record is reached only
with constructed evidence; actual owners cannot produce one.

`lifecycle_lostreply_test.go` arms the fixture through the real endpoint (and
the CLI client) on the same real runtime. The main subtest arms code 2: a
GETATTR CALL accepted after arming is delivered normally, then an actual MKDIR
CALL commits its journal effect (the record names `dropped_opcode` MKDIR);
the C exporter's actual result pread then receives EIO from the
real `Transport.Read`, and that guest FETCH delivers no bytes. Evidence shows
the claim, protected response and committed source change with no coverage.
QUERY reconciles the original OK result, the retry delivers the retained bytes,
and after FORGET plus a view refresh the real C9 restart preserves the response
bytes, result, source identity and a single directory entry. A second subtest
shows C9 refusing (FENCED) while the dropped response is still unread.
Negative cases cover a foreign peer UID, foreign runtime, stale cut and epoch,
operations 0/3/255, an unknown session, a short frame, an exhausted actual
budget, repeated ARM, ARM after restart, a foreign session's CALL and expiry
of an unfired fixture at C9; `TestLifecycleClientArmTargets` checks the
client's `--lost-intent` mapping onto the unchanged 57-byte frame.
`internal/guestbridge/lost_reply_test.go` covers the predicate, including the
MKDIR filter passing an earlier non-matching CALL, on a real bridge service. The test C fixture's guest emulation
reports every non-data FETCH reply as EAGAIN, so the native EIO is observed at
its actual pread boundary. Native FreeBSD execution, the native lost-reply and
compatibility acceptance and the real 9p base gate (zq3) remain unrun and
unclaimed.
