# xz3 964 kernel rebuild (2026-11-10): fixed 9p tag reused only after release

This candidate supersedes the [z54 candidate](../xz3-20261109e/README.md)
(`2e0412a6…`, source `a20aca1`) only because its guest kernel predates 964.
In lab run zq3-r5 (R5-1) the release loop's VIEW_QUERY and the event worker's
VIEW_ACK shared fixed 9p tag 65533. `p9_client_hfs_exchange` let the next
owner allocate the tag before the previous request was released, so
`idr_alloc` failed with ENOMEM. `hfs_control` then blocked the session, and
DRAINED was never sent. Task 964 (merge `06c27a8`) changed patches 0001, 0003,
0004 and 0005 and `source.json`. The exchange now waits, bounded, until the
previous request on the tag is released. `hfs_transport` retries a busy tag
without blocking the session. The y54 kernel-only method was used again:
rebuild the kernel, reuse everything else. **Build and offline admission
only:** nothing was installed or booted, and `installed`, `booted` and
`native_accepted` stay false with publication null.

## Reproducibility

`kernel.py` ran its four stages twice, each under a user systemd scope (two
CPUs, 2 GiB, no swap) with a 20-minute timeout, at the **same** canonical
output path `…/hfs-xz3-20261110f/kernel-build`. The output path is a recorded
compile input, so the first build tree was moved to `kernel-build-first`
before the repeat. `abi.py collect` ran on both packages before
`compare_kernel.py`, which passed on the first attempt: identical compile
inputs, all 13 artifacts and the full module ABI. `check_abi_mismatch.py`
refused its four negative controls.

Against the prepared source, three suites passed:
- `tests/mount_hello/run.py --sanitize`: all five cases;
- `tests/tag/run.py --sanitize`: all four 964 fixed-tag cases;
- the `controlled_received` `terminal-smoke` scenario, including the 964
  `BUSY_TAG`/`BUSY_TAG_CHECK` path and the w54 startup regressions.

## Admission and checks

The worker sandbox refuses git in the main checkout, so the build and
assembly ran from the worker worktree at `06c27a8`. All 3953 tracked files
are byte-identical to the main checkout, which is also at `06c27a8`. The main
checkout has no untracked files under `cmd`, `internal`, `pkg`,
`tools/integration` or `tools/lab`. The reused daemon's builder bindings
named the 664 worktree (`.claude/worktrees/agent-a6a14d11158c35366`), where
the daemon was actually built. They were re-keyed to this worktree, but only
after checking that `daemon.py` (`57083443…`) and `daemon_cgo.py`
(`6538e95f…`) there hash exactly to the bound values. **This departs from
w54/z54 practice**, where `assemble.py` ran from the checkout that built the
daemon, so the bindings named the real build path. Here the bindings name a
path where the daemon was never built. That is harmless because the daemon
bytes and both recipe hashes are identical, but it is a deviation. The
original binding files (naming the real build path) are kept in the run root
under `daemon-binding-origin/`. Every other reused proof record is a byte
copy.

`assemble.py` sealed and admitted the package. An independent `admit.py` run
against the pinned manifest passed. `check_candidate.py` refused all
26 real-copy mutations for their expected reasons, including the real
CGO0 daemon `480713c2…`. The original and the restored copy passed again.

The tooling now admits only this manifest. The z54 `2e0412a6…`, w54
`89c928d5…`, r54 `5eb42c50…`, f44 `b203799e…` and earlier `3f770a88…` are
refused as superseded, and `7e962627…` stays quarantined. The f3 observer
qualification of the daemon carries over, because zq3-r5 qualified these
exact bytes. Booting this kernel and mounting through it remain zq3 steps
that need explicit approval.
